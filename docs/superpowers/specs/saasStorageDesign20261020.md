# Toonflow SaaS 存储架构设计

**状态：** 待用户审阅

**日期：** 2026-10-20

## 目标

为 Toonflow 的 SaaS 服务部署提供集中、持久并按用户隔离的存储：PostgreSQL 保存用户身份、用户元数据、会话元数据和工作区索引；阿里云 OSS 的 S3 兼容接口保存工作区文件、Agent 历史文件和生成媒体。生产服务由 Docker Compose 管理。

这次面向新 SaaS 部署，不导入现有 `data/` 文件，不把桌面端作为交付目标。

## 已确认的边界

- 身份和数据按 SXWZ 用户隔离；当前版本不引入组织、课程或团队租户层。
- 用户姓名和 SXWZ `sessionId` 以明文写入 PostgreSQL，不做字段级 hash 或应用层加密。
- Toonflow 自己签发的 Cookie 会话令牌只存 SHA-256 哈希；原始 SXWZ 登录 Token 不持久化。
- 工作区文件与媒体内容的权威副本位于私有 OSS bucket。
- 前端以 `workspaceId` 和工作区相对路径寻址，不传服务器绝对路径。
- 现有模型目录继续由算力中台控制；本设计不复制模型目录或改变模型授权。
- 不使用 OSSFS 伪装本地文件系统。

## 当前实现约束

- SXWZ 用户配置目前是每用户 `settings.json`；身份映射和登录会话目前写入 `data/auth/*.json`。
- SXWZ 用户工作区目前位于 `<data>/users/<userId>/workspaces`，会话和媒体以普通文件落盘。
- 工作区路由、Agent SDK、附件处理、画布和媒体代码直接依赖 POSIX 文件操作及绝对目录路径。
- Agent 活动会话、工作区锁和用户配置缓存包含进程内状态；多实例运行前需处理共享状态及写入协调。
- 当前 `compose.yaml` 只有 Toonflow 服务与 `data/` 命名卷，没有 PostgreSQL 或 OSS 配置。

## 架构

### PostgreSQL

PostgreSQL 是用户、身份、会话和工作区元数据的权威存储。使用应用级 SQL 仓储与版本化 SQL migration，不把数据库调用散落在 HTTP 路由中。

核心数据关系：

- `users`：内部 UUID、显示名称、状态和时间戳。
- `external_identities`：provider、明文 `external_subject`、`user_id`；`(provider, external_subject)` 唯一。SXWZ `sessionId` 作为外部身份标识。
- `sessions`：本地 Cookie 令牌哈希、所属用户、过期及撤销时间。
- `user_settings`：按用户保存 JSONB 设置。
- `workspaces`：UUID、所有者用户、名称和创建/修改时间。
- `workspace_entries`：工作区相对路径、文件或目录类型、对象引用、内容类型、大小、内容 revision 和时间戳；`(workspace_id, path)` 唯一。
- `storage_outbox`：记录对象删除等需跨 PostgreSQL 和 OSS 重试的清理动作，避免数据库提交后因 OSS 暂时不可用而遗留不可追踪对象。

身份绑定依赖 SXWZ `sessionId` 对同一用户保持稳定且唯一。当前代码已把该字段作为外部身份使用；上线前需确认上游在用户重新登录或 Token 更新后仍返回同一身份值。若上游不保证稳定，须使用 SXWZ 提供的稳定用户标识，不以姓名合并用户。

所有工作区数据库查询都必须同时限定当前已认证的 `user_id` 和 `workspace_id`。客户端传入的用户 ID、对象键或绝对路径不得用于授权判断。

### OSS

- 通过 `@aws-sdk/client-s3` 的 S3 兼容 API 访问阿里云 OSS；生产配置提供 endpoint、region、bucket 和服务端访问凭证。
- bucket 默认私有。对象键由服务端生成，不直接使用客户端文件名作为对象键；数据库索引保存逻辑路径到对象引用的映射。
- 浏览器上传/下载仅获得短时、单对象预签名 URL。签发前验证用户对工作区和相对路径的权限；上传完成后检查 OSS 对象存在、大小和内容类型，再提交索引记录。
- 媒体生成由服务端接收供应商结果并写入 OSS。参考媒体由服务端按已授权对象读取或签发短时读取地址。
- OSS 不提供目录和原子 rename 语义：目录与路径关系由 `workspace_entries` 表表示；移动/重命名在 PostgreSQL 事务中更新路径索引，不复制对象内容。
- 上传先写入新对象，再以 revision 条件更新 PostgreSQL 索引；索引提交失败产生的孤儿对象由清理流程回收。删除先从用户可见索引中移除并写 outbox，再异步删除对象；清理失败可重试。

### 工作区运行时

建立服务端 `WorkspaceStore` 作为工作区文件的业务入口，提供授权后的目录列表、读取、写入、创建、复制、移动/重命名和删除等操作。工作区相对路径须在服务端规范化并拒绝遍历路径、绝对路径和保留路径。

Agent SDK 当前要求 POSIX `cwd` 和会话文件。SaaS 运行时使用服务端临时工作区 checkout 适配这一边界：从 PostgreSQL 索引和 OSS 还原工作区，运行现有路径型 Agent/插件，然后将所有新增、修改和删除同步回 OSS 与 PostgreSQL 后再结束操作。Agent 会话须在用户消息接受、assistant 消息结束、工具执行结束及明确保存点建立可恢复检查点；未完成的流式回复在进程崩溃时允许标记为中断。临时 checkout 不作为权威副本，容器重启后可丢弃并从 OSS 重建。

同一工作区的写操作需要服务级租约或 PostgreSQL 锁协调。第一版生产 Compose 只运行一个 Toonflow 应用副本；在活动 Agent 会话可跨实例恢复、锁和流式控制可共享前，不宣称支持多个应用副本并行处理同一会话。

### Docker 生产部署

- Compose 至少包含 `toonflow`、`postgres` 和一次性 `migrate` 服务；应用只在数据库健康且 migration 完成后启动。
- PostgreSQL 使用命名卷和健康检查，不发布公网端口。应用数据经 DB 与 OSS 持久化；应用容器可重建。
- OSS 是外部托管服务，不在 Compose 中模拟。OSS 凭证通过部署环境或 Docker secrets 注入，不提交到仓库或镜像。
- 保留现有反向代理拓扑；应用端口仅绑定 loopback 或内部网络。健康检查区分应用存活与数据库/OSS 依赖可用性。
- 数据库 migration 必须是幂等、有版本记录的单次操作；不由每个应用副本并发执行。

## 数据一致性和失败处理

- 文件上传：先上传不可变对象，再用数据库事务条件更新 entry revision；数据库失败时对象不对用户可见，后续由清理任务回收。
- 文件替换：仅在客户端 revision 与当前值一致时更新索引，冲突返回 409，避免静默覆盖并发编辑。
- 删除：在数据库事务中隐藏 entry 并写 outbox；OSS 删除由后台重试完成。对象清理不能让失败的数据库事务变成用户数据丢失。
- outbox 由单个应用实例内的后台循环分批读取并处理；失败项保留在数据库中并按退避策略重试，成功后标记完成。
- OSS 不可用时，禁止报告上传、保存或生成成功。读取和写入错误按现有 API 错误结构返回，不吞掉异常或无条件重试。
- 用户注销只撤销数据库会话；删除用户及其数据应由明确的数据删除流程完成，按工作区清理索引、OSS 对象和设置，避免登录退出误删内容。
- PostgreSQL 备份与恢复需要包含 schema migration 状态；OSS 需启用适当的版本/生命周期策略，并定期验证数据库索引与对象引用可恢复。

## 非目标

- 迁移旧 `data/`、旧 JSONL 会话或用户本地工作区。
- 桌面端本地模式、离线同步、跨设备桌面目录挂载。
- 组织/学校/课程级租户、计费与配额系统。
- Redis、通用任务队列或多区域部署。
- 改造算力中台模型目录、SXWZ 登录验证协议或 AIGC 模型调用协议。

## 验收标准

1. 新 SaaS 环境通过 Docker Compose 启动，PostgreSQL migration 成功，应用健康检查通过。
2. 登录后用户身份和用户元数据写入 PostgreSQL；同一 SXWZ `sessionId` 映射到同一内部用户；本地 Cookie 会话令牌只以哈希形式落库。
3. 用户工作区、目录索引、Agent 历史文件、画布和媒体内容在 OSS/数据库中持久化；重建 Toonflow 容器后可恢复并访问。
4. 用户不能通过伪造 workspaceId、相对路径、对象键或预签名参数读取、覆盖或删除其他用户数据。
5. 并发编辑返回明确冲突；PostgreSQL 或 OSS 失败不会向客户端报告成功；孤儿对象和失败删除可被清理流程重试。
6. 临时 checkout 不是持久数据源；正常结束时完成写回；崩溃后已提交检查点可恢复，未完成回复显示为中断。
7. 现有工作区文件 API 的核心行为（列表、读写、重命名、复制、删除、媒体导入/生成、Agent 历史）在 SaaS 存储实现下保持一致。

## 主要风险

- Agent SDK 和多个插件依赖本地路径；checkout 和可靠检查点会是工作区改造的主要工程量。
- PostgreSQL 与 OSS 无跨服务事务，必须依赖不可变对象、事务化索引更新、outbox 和可重试清理。
- 预签名上传若未完成确认，可能留下孤儿对象；若路径索引先提交，可能出现缺失对象。流程顺序和清理任务必须按本设计实现。
- `sessionId` 明文存储是明确产品决策；需限制数据库访问、日志输出和运维导出范围，不能把该值写入普通请求日志。
- 单副本约束是第一版对活动 Agent 会话进程内状态的限制；水平扩容需单独设计会话所有权与流式协调。
